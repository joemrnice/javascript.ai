ESM vs CommonJS

JavaScript has two module systems in production use today. Knowing which one you're in — and why they don't always play nicely together — solves a huge share of real-world "cannot use import statement" errors.

CommonJS (CJS) — Node's original system

math.cjs
// Exporting
function add(a, b) { return a + b; }
module.exports = { add };
// or: exports.add = add;

// Importing — synchronous, resolved at require() call time
const { add } = require("./math.cjs");
add(2, 3);

CJS require() is synchronous and can be called conditionally, anywhere in a file — inside an if, inside a function. Modules are cached after the first load — every subsequent require() of the same file returns the same object.

ESM (ECMAScript Modules) — the language standard

math.mjs
// Named exports
export function add(a, b) { return a + b; }
export const PI = 3.14159;

// Default export — one per module
export default function multiply(a, b) { return a * b; }

// Importing
import multiply, { add, PI } from "./math.mjs";
import * as math from "./math.mjs"; // namespace import — math.add, math.PI

// Dynamic import — the ESM escape hatch for conditional/lazy loading
const { add: lazyAdd } = await import("./math.mjs");

Why ESM enables tree-shaking

Because ESM import/export statements are static (fixed, analyzable without running the code), a bundler can build a complete dependency graph and delete exports nobody imports. CommonJS's require() can happen inside conditionals with dynamic paths, so bundlers generally can't prove a given export is unused.

Using ESM in the browser

index.html
<script type="module">
  import { add } from "./math.mjs";
  console.log(add(2, 3));
</script>

<!-- Modules are automatically deferred and strict-mode by default,
     and each module only executes once, no matter how many times it's imported. -->

Interop: using both together

interop.js
// ESM importing a CommonJS package — usually fine, Node wraps it automatically
import express from "express"; // express ships as CJS; this "just works" in Node ESM

// CommonJS CANNOT statically `require()` an ESM-only package — must use
// dynamic import instead, because require() is synchronous and ESM loading isn't:
async function loadEsmOnlyPkg() {
  const { default: chalk } = await import("chalk"); // chalk v5+ is ESM-only
  return chalk;
}

Why bundlers still exist in an ESM world

Native ESM works in every modern browser, so in theory you don't need a bundler at all for module resolution. In practice, tools like Vite, esbuild, Webpack, and Rollup still earn their keep for: bundling hundreds of small files into fewer requests, transpiling TypeScript/JSX, minification, code-splitting for lazy-loaded routes, and handling non-JS assets (CSS, images) through import.

Interview questions on this topic

require() is synchronous and can be called conditionally anywhere in a file, since CommonJS resolves at runtime. import is static — bindings are resolved before any code runs, and (outside of dynamic import()) it can only appear at the top level of a module, never inside an if or function.

With dynamic import(), which returns a promise: const mod = await import("./feature.js"). This is the standard way to code-split a route or defer loading a heavy dependency until it's actually needed.

The runtime is treating the file as CommonJS by default. Fix it by renaming the file to .mjs, adding "type": "module" to package.json (Node), or adding type="module" to the <script> tag (browser).
