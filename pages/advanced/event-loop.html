Execution Context & Event Loop

JavaScript is single-threaded — one call stack, one thing at a time. Everything asynchronous (timers, network requests, DOM events) is handled by APIs outside the engine, coordinated by the event loop. This is the single most-asked systems question in JS interviews.

The building blocks

PieceWhat it does
Call stackTracks function calls, one frame per active call. LIFO — last in, first out.
HeapWhere objects are allocated in memory.
Web APIs / Node APIsProvided by the browser/runtime, not the JS engine: setTimeout, fetch, DOM events, file I/O.
Microtask queuePromise callbacks (.then, async/await continuations), queueMicrotask. Higher priority.
Macrotask (task) queuesetTimeout, setInterval, I/O, UI events. Lower priority.
Event loopContinuously checks: is the call stack empty? If so, drain the entire microtask queue, then run one macrotask, then repeat.

The rule that decides most "predict the output" questions

Priority order

1. Run all synchronous code on the call stack to completion.
2. Drain the entire microtask queue (all pending promises), even if new microtasks keep getting added.
3. Run exactly one macrotask.
4. Go back to step 2.

predict-the-output.js
console.log("1: sync start");

setTimeout(() => console.log("2: macrotask (setTimeout)"), 0);

Promise.resolve().then(() => console.log("3: microtask (promise)"));

console.log("4: sync end");

// Output order:
// 1: sync start
// 4: sync end
// 3: microtask (promise)      ← microtasks always drain before the next macrotask
// 2: macrotask (setTimeout)   ← even with a 0ms delay
nested-microtasks.js
console.log("A");

setTimeout(() => console.log("B"), 0);

Promise.resolve()
  .then(() => {
    console.log("C");
    return Promise.resolve();
  })
  .then(() => console.log("D"));

Promise.resolve().then(() => console.log("E"));

console.log("F");

// A, F, C, E, D, B
// The microtask queue keeps draining — C's chained .then (D) still
// runs before the setTimeout callback (B), because the queue isn't
// considered "empty" until every microtask, including newly-queued
// ones, has run.

The call stack and stack overflow

call-stack.js
function third()  { console.trace(); }     // stack: [main, first, second, third]
function second() { third(); }             // stack: [main, first, second]
function first()  { second(); }            // stack: [main, first]
first();                                     // stack: [main]

// A function with no base case blows the stack:
function recurse() { return recurse(); }
recurse(); // RangeError: Maximum call stack size exceeded

Why this matters for the UI thread

Because there's one thread, a long synchronous task — like sorting a huge array — blocks everything: clicks, renders, scroll, timers. This is why expensive work gets chunked (via setTimeout/requestIdleCallback) or moved to a Web Worker, which runs on a genuinely separate thread with no shared memory (communication happens via postMessage).

Interview questions on this topic

Yes, the JS engine itself runs on one thread with one call stack. Asynchronous behavior comes from the surrounding runtime (browser or Node), which offloads work like timers and network requests to separate mechanisms, then schedules the corresponding callbacks back onto the JS thread via the event loop once the main stack is clear.

Microtasks (promise callbacks, queueMicrotask) are drained completely, in full, before the event loop is allowed to process even a single macrotask (setTimeout, UI events, I/O). This means promise-based code always "wins" a race against a setTimeout(0).

No. 0ms is a minimum delay, not a guarantee — the callback still has to wait for the current synchronous code to finish, the entire microtask queue to drain, and (in browsers) is often clamped to a ~4ms minimum after several nested timeouts. It always runs after any already-queued microtasks.

A Web Worker runs JavaScript on a separate OS thread, isolated from the main thread's memory — communication happens only via serialized messages (postMessage/onmessage). Use it for CPU-heavy work (image processing, large sorts/parses, complex calculations) that would otherwise freeze the UI, since it has no access to the DOM directly.
