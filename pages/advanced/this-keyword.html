The this Keyword

this is not determined by where a function is written — it's determined by how the function is called. That single rule resolves 90% of "why is this undefined" bugs.

The four binding rules

In order of precedence, from weakest to strongest:

1. Default binding — plain function calls

default-binding.js
function whoAmI() { console.log(this); }
whoAmI();
// Non-strict mode: `this` is the global object (window / globalThis)
// Strict mode ("use strict"): `this` is undefined

2. Implicit binding — called as a method

implicit-binding.js
const user = {
  name: "Zainab",
  greet() { console.log(`Hi, I'm ${this.name}`); },
};
user.greet(); // "Hi, I'm Zainab" — this = user, the object left of the dot

const detached = user.greet;
detached(); // "Hi, I'm undefined" — this LOST its binding; called plainly now

3. Explicit binding — call, apply, bind

explicit-binding.js
function introduce(greeting) { return `${greeting}, I'm ${this.name}`; }
const person = { name: "Tunde" };

introduce.call(person, "Hello");      // args passed individually — "Hello, I'm Tunde"
introduce.apply(person, ["Hi"]);      // args passed as an array — "Hi, I'm Tunde"

const bound = introduce.bind(person); // returns a NEW function, permanently bound
bound("Hey");                          // "Hey, I'm Tunde" — even if called detached later

4. new binding — constructor calls

new-binding.js
function Car(model) {
  this.model = model; // `this` = the brand-new object `new` just created
}
const car = new Car("Corolla");
console.log(car.model); // "Corolla"

// `new` does four things:
// 1. Creates a new empty object
// 2. Links its prototype to Car.prototype
// 3. Calls Car with `this` bound to the new object
// 4. Returns the new object (unless the function explicitly returns another object)

Arrow functions: no this of their own

Arrow functions don't have their own this. They capture it lexically from the enclosing scope at the moment they're defined — none of the four rules above apply to them.

arrow-this.js
const timer = {
  seconds: 0,
  start() {
    // Arrow function inherits `this` from start()'s scope — the timer object
    setInterval(() => { this.seconds++; }, 1000);
  },
  startBroken() {
    // Regular function loses `this` — setInterval calls it plainly
    setInterval(function () { this.seconds++; }, 1000); // this = undefined/window, breaks
  },
};

timer.start(); // works — this.seconds increments correctly
Practical rule

Use regular functions (or method shorthand) for object methods and anything called with new. Use arrow functions for callbacks nested inside a method, where you want this to keep pointing at the outer object.

Precedence, all together

precedence.js
function show() { console.log(this.label); }
const objA = { label: "A", show };
const objB = { label: "B" };

objA.show();                 // "A" — implicit binding
objA.show.call(objB);        // "B" — explicit beats implicit
const boundToB = show.bind(objB);
boundToB.call(objA);         // "B" — bind is permanent; call can't override it
new boundToB();                // {} — `new` even beats a hard bind, creating a fresh object

Interview questions on this topic

How the function is called, not where it's defined (with the one exception of arrow functions, which inherit this lexically). The four rules in order of precedence: new binding > explicit binding (call/apply/bind) > implicit binding (method call) > default binding (plain call).

All three explicitly set this. call(thisArg, a, b, c) invokes the function immediately with arguments listed individually. apply(thisArg, [a, b, c]) invokes immediately with arguments as an array. bind(thisArg) doesn't invoke anything — it returns a new function permanently bound to thisArg, to be called later.

Because setTimeout invokes the callback as a plain function call — no object precedes it — so default binding kicks in (undefined in strict mode). Fix it with an arrow function (to inherit the surrounding this) or with .bind(this).
