Promises & async/await

Three eras of the same problem — "run this after that finishes" — from nested callbacks, to chainable promises, to code that reads top-to-bottom again. Understand what async/await is doing underneath, not just how to type it.

Callback hell (the problem)

callback-hell.js
getUser(userId, (err, user) => {
  if (err) return handleError(err);
  getOrders(user.id, (err, orders) => {
    if (err) return handleError(err);
    getOrderDetails(orders[0].id, (err, details) => {
      if (err) return handleError(err);
      render(details); // four levels deep, error handling repeated at every level
    });
  });
});

Promises: a value that will exist eventually

A promise is an object representing the eventual result of an async operation. It's always in one of three states: pending, fulfilled, or rejected — and once settled, it never changes state again.

promise-basics.js
function fetchUser(id) {
  return new Promise((resolve, reject) => {
    setTimeout(() => {
      if (id > 0) resolve({ id, name: "Amara" });
      else reject(new Error("Invalid id"));
    }, 500);
  });
}

fetchUser(1)
  .then(user => user.name)         // each .then returns a NEW promise
  .then(name => name.toUpperCase())
  .then(name => console.log(name)) // "AMARA"
  .catch(err => console.error(err.message)) // catches ANY rejection above
  .finally(() => console.log("done — always runs"));

async/await: promises with synchronous-looking syntax

async/await is not a new concurrency model — it's syntax sugar over promises. An async function always returns a promise; await pauses execution of that function (not the whole program) until the awaited promise settles.

async-await.js
async function loadUserOrders(userId) {
  try {
    const user = await getUser(userId);       // pauses here, non-blocking to the rest of the app
    const orders = await getOrders(user.id);   // then here
    const details = await getOrderDetails(orders[0].id);
    return details;
  } catch (err) {
    // try/catch replaces .catch() — one place for every await above to fail into
    handleError(err);
  }
}

// Equivalent promise chain, for comparison:
function loadUserOrdersPromises(userId) {
  return getUser(userId)
    .then(user => getOrders(user.id))
    .then(orders => getOrderDetails(orders[0].id))
    .catch(handleError);
}
Sequential awaits are a common performance bug

Awaiting independent promises one at a time makes them run sequentially, not in parallel — even though they don't depend on each other.

parallel-vs-sequential.js
// ❌ Sequential — total time = sum of all three (slow)
const user = await fetchUser();
const posts = await fetchPosts();
const comments = await fetchComments();

// ✅ Parallel — total time = the SLOWEST of the three
const [user2, posts2, comments2] = await Promise.all([
  fetchUser(), fetchPosts(), fetchComments(),
]);

The Promise combinators

MethodResolves whenRejects when
Promise.all()Every promise fulfillsAny one rejects (fails fast)
Promise.allSettled()Every promise settles (fulfilled or rejected)Never — gives you a status for each
Promise.race()The first promise to settle, whatever it isIf the first to settle is a rejection
Promise.any()The first promise to fulfillOnly if ALL of them reject
allsettled.js
const results = await Promise.allSettled([
  fetchUser(1), fetchUser(-1), fetchUser(2),
]);
// [
//   { status: "fulfilled", value: {...} },
//   { status: "rejected",  reason: Error("Invalid id") },
//   { status: "fulfilled", value: {...} },
// ]
// Unlike Promise.all, one failure doesn't discard the others' results.

Common pitfalls

pitfalls.js
// ❌ Forgetting to return inside a .then chain breaks the chain
promise.then(result => {
  doSomethingAsync(result); // not returned — the NEXT .then gets undefined immediately
}).then(x => console.log(x)); // undefined, doesn't wait for doSomethingAsync

// ❌ await outside a for...of loop still runs in a loop but forEach can't await
[1, 2, 3].forEach(async n => { await doWork(n); }); // fires all 3 in parallel, uncontrolled,
                                                       // and the outer function does NOT wait

// ✅ Use for...of with await when you genuinely need sequential processing
for (const n of [1, 2, 3]) { await doWork(n); }

// ✅ Use Promise.all(arr.map(...)) when order doesn't matter and you want parallelism
await Promise.all([1, 2, 3].map(n => doWork(n)));

Interview questions on this topic

Pending (initial, neither fulfilled nor rejected), fulfilled (the operation completed successfully), and rejected (the operation failed). Once a promise moves to fulfilled or rejected — collectively called "settled" — it can never change state again.

No. await only pauses execution within the current async function; control returns to the event loop, which keeps handling other code, UI events, and timers. When the awaited promise settles, the rest of the async function resumes as a microtask.

Promise.all rejects immediately if any single promise rejects, discarding the results of the others. Promise.allSettled always resolves once every promise has settled, returning a status/value or status/reason object for each — useful when you want results even from operations that failed.

Wrap the await calls in a standard try/catch block — a rejected awaited promise throws inside the async function, exactly like a synchronous exception. For multiple independent calls, consider whether one failure should stop everything (try/catch around Promise.all) or should be handled individually (Promise.allSettled).
